# Writable volume integrity

Writable volumes use a fixed dm-crypt authenticated-encryption table above
dm-integrity. The latter stores the 32-byte data MAC and 16-byte random IV for
each 4096-byte block. This profile additionally enables the stock kernel's
`journal_mac:hmac(sha256)` and `fix_hmac`. Go builds one fixed superblock format
and requires the on-disk snapshot to match it exactly before opening a volume.

## Protected header

The existing volume is read once into a 4096-byte snapshot. Go constructs a
new zero-filled header, sets every configuration field from its fixed profile
and calculated layout, retains only the 16-byte format salt, and computes the
expected HMAC. A constant-time comparison of the entire snapshot against this
header verifies both authentication and the exact format, including all zero
recovery/reserved bytes. Disk flags cannot disable this check. Mismatches are
rejected, not repaired or interpreted as another format.

The Go-built bytes are placed in an anonymous file on a private `tmpfs,noswap`
mount. A loop device exposes that file as a block device. A two-target dm-linear
mapping presents the following device to dm-integrity:

| Logical sectors | Backing |
| --- | --- |
| 0 through 7 | Guest-private 4 KiB header file |
| 8 through the end | Identical sectors of the raw disk |

Both constructor and resume superblock reads use the protected prefix.
Changing the raw disk's superblock after Go's read cannot change the kernel's
configuration. This uses stock loop, dm-linear and tmpfs functionality already
present in the CVM kernel. No kernel patch, new module or userspace daemon is
required. The existing boot and volume-worker capabilities permit these
operations.

The file and its mount are anonymous/detached after setup. Loop autoclear and
device-mapper references keep it alive after the volume worker exits and
release it when the mappings are removed. The mount must support `noswap`;
failure is fatal. The trusted guest kernel can write the file. The VMM cannot
modify its contents through storage I/O or force it to swap to the raw disk.
Guest-root compromise is outside this boundary.

## Fixed profile and keys

The implementation supports only this profile; it has no version negotiation
or compatibility branches:

| Header field | Source of kernel-facing value |
| --- | --- |
| Magic / version | `integrt\0` / 5, fixed in Go |
| Tag size / block-size log | 48 bytes / 3 (4096-byte blocks), fixed in Go |
| Interleave log | 15 (32768 sectors), fixed in Go |
| Flags | Exactly `0x19`: journal MAC, fixed padding, fixed HMAC |
| Journal sections / data sectors / bitmap log | Calculated in Go from bounded device size and the fixed layout |
| Recalculation position / reserved bytes | Zero |
| Salt | Authenticated 16-byte value generated by the kernel at format time |
| Superblock MAC | Recomputed HMAC-SHA256 with the derived metadata key |

The device-mapper table also fixes journal mode J, all offsets, algorithms,
buffer size, commit interval and watermark. Bitmap mode, recalculation, inline
mode and unknown flags are unsupported. The salt is the only header field
retained from disk, and only after the full header comparison succeeds. It is
not a secret or configuration selector. Hardcoding or replacing it would
invalidate the journal MACs created with that per-format salt.

Journal sizing follows the pinned kernel's rule (device sectors / 128, capped
at 131072 sectors, rounded to whole journal sections). Go calculates capacity
and the kernel's bitmap-granularity field from this fixed layout; it does not
use the on-disk capacity as authority. Reported device size is bounded and
captured in the linear table for the mount's lifetime. Resizing is unsupported.

A separate 32-byte metadata key is derived from the existing 64-byte volume key
with HKDF-SHA256, no salt, and info consisting of
`tinfoil volume integrity metadata key v1`, a NUL byte, and the measured volume
name. The data-key derivation and RTMR seal identity remain unchanged. The new
key is erased from Go's temporary buffers; the keyed table also uses
`DM_SECURE_DATA_FLAG`. No client key-file or unlock protocol change is needed.

Fresh initialization gives the kernel a trusted zero prefix, allowing it to
generate the v5 superblock, salt, MAC and initial journal. Go requires the
generated header to exactly match its own fixed header before activation, and
persists the Go-built header to the raw disk for subsequent boots. Both format
and open use a single integrity table load at the Go-calculated capacity: no
temporary probe mapping, kernel-discovered capacity, or second table load is
needed. Normal writes and journal recovery do not change the fixed superblock
in this profile. Kernel superblock writes during the mount go to the private
prefix.

## Scope and limits

This writable-volume feature has not been deployed in production, so the
implementation deliberately supports only newly initialized volumes in this
format and reopening those volumes. Other formats fail the same fixed-profile
check; there is no legacy reader, conversion, or reformat fallback. Formatting
still requires an explicitly permitted blank volume, so removing compatibility
does not mean overwriting existing data. Volume names are bound into the
metadata key; renaming and resizing existing volumes are unsupported.

The superblock MAC authenticates its configuration. The journal MAC protects
journal sector addresses, and dm-crypt authenticates data, IVs and logical
sector numbers. This does not provide rollback protection, freshness, or
availability against the storage provider. Journal/data reads still come from
the host; this change removes the superblock reread race specifically.

## Validation

From `tinfoil/`, run `go test ./...`. The header tests reject modifications
throughout the 4 KiB snapshot, reject changes to every fixed-profile byte even
with a recomputed MAC, and verify that the generated header retains only the
authenticated salt without aliasing the snapshot. These tests do not pass
malformed superblocks to the kernel.

The opt-in test can be built with
`go test -c -tags integration -o /tmp/tinfoil-integrity.test ./internal/devicemapper`
and run as root with `TINFOIL_INTEGRITY_INTEGRATION=1` and
`-test.run '^TestIntegrityKernelRoundTrip$' -test.v`. It creates its own temporary
64 MiB image and loop devices; it never accepts an existing disk path. It
checks initialization, kernel/Go format agreement, encrypted block writes at
both ends of the mapping, close/reopen, wrong-key rejection, protected-prefix
reads and suspend/resume after changing the raw prefix, and mapping cleanup.
